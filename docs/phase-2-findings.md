# Phase 2 findings

- **Date:** 2026-11-05
- **Scope:** the proof of concept with plain Logback, research on Error Prone and NullAway, the
  status of jqwik and Jazzer, and verification of the Logback facts stated in `docs/spec.md`
  (section 8, plus the related items in section 10.1).
- **Rule followed:** when a finding contradicts the spec, it is recorded here and raised with the
  maintainer. No approved decision was changed (CLAUDE.md, "Decisões").

## 1. Proof of concept: the implicit `%ex` bypass

### 1.1 What was tested

`securedatamasker-logback/src/test/java/io/github/jhonwesleyy/securedatamasker/logback/poc/ImplicitThrowablePocTest.java`
uses **plain Logback only**: no SecureDataMasker class is loaded. Each test builds a fresh
`LoggerContext` and an `OutputStreamAppender` that writes to memory. It then logs:

```java
logger.error("payment rejected for customer {}", "123.456.789-09",
        new IllegalStateException("invalid document 123.456.789-09"));
```

`123.456.789-09` is fictitious: it was generated by the CPF check-digit algorithm from the base
`123456789`, and the spec uses it as its example.

| # | Encoder / pattern | Expected and observed |
| --- | --- | --- |
| 1 | `%msg%n` (no `%ex`) | The throwable **is appended anyway**: class, message with the CPF in clear, and `\tat` stack frames |
| 2 | `%replace(%msg){'\d{3}\.\d{3}\.\d{3}-\d{2}', '***.***.***-**'}%n` | The first line is masked, but the implicit throwable still prints the CPF **in clear** |
| 3 | `%msg%n%nopex` | Only the message line; no throwable |
| 4 | `%replace(%msg%n%ex){…}` | No CPF in clear anywhere. The throwable is printed **once**: a throwable converter nested inside a composite converter counts, so `PatternLayout` does not append its own |
| 5 | `JsonEncoder` (native) | Writes `"message":"payment rejected for customer {}"`, `"arguments": ["123.456.789-09"]` and the throwable message in clear. No `PatternLayout` is involved |
| — | Version check | The test asserts that the loaded `logback-classic-<version>.jar` is the one requested with `-Dlogback.version` |

### 1.2 Results per version

Command, run once per version on JDK 25.0.4.1:

```bash
mvn -B clean verify -Dlogback.version=<version>
```

| Logback | Skeleton compiles | PoC (6 tests) | Jar actually loaded |
| --- | --- | --- | --- |
| 1.5.18 (control, below the minimum) | yes | pass | `logback-classic-1.5.18.jar` |
| **1.5.19** (minimum) | yes | **pass** | `logback-classic-1.5.19.jar` |
| **1.5.38** (latest 1.5.x on 2026-11-05) | yes | **pass** | `logback-classic-1.5.38.jar` |
| 1.6.6 (latest overall on 2026-11-05) | yes | pass | `logback-classic-1.6.6.jar` |

The behavior is identical across all four versions. In the sources, `EnsureExceptionHandling.java`
differs between 1.5.19, 1.5.38 and 1.6.6 only in its license header: copyright years, and EPL v1.0
replaced by v2.0.

### 1.3 Minimum supported version: 1.5.19

- **Not set by behavior:** the PoC passes on 1.5.18 too.
- **Set by security:** CVE-2025-11226 (arbitrary code execution through `<if>` conditions in the
  configuration) affects all versions before 1.3.16 and versions 1.4.0 up to, but not including,
  1.5.19. It is fixed in **1.5.19** and 1.3.16 ([GitLab advisory][gitlab-cve]). 1.3.x needs only
  Java 8 and is outside the 1.5.x line the spec targets.
- **API:** everything the skeleton uses (`CompositeConverter`, `PatternLayoutEncoder`,
  `ILoggingEvent`) compiles unchanged from 1.5.19 to 1.6.6.

The minimum is 1.5.19. This agrees with spec section 10.1 ("minimum ≥ 1.5.19") and is recorded in
ADR-007.

### 1.4 Notes for Phase 5 from the PoC and the sources

1. **Converter registration differs between 1.5 and 1.6.** Logback 1.6.0 removed
   `PatternLayout.defaultConverterMap` and `getDefaultConverterMap()`. In 1.6.6 they are commented
   out in `PatternLayoutBase`, and Apache SkyWalking reported breakage
   ([skywalking#14120][skywalking]). `PatternLayoutBase.getInstanceConverterMap()`, which returns
   `Map<String, Supplier<DynamicConverter>>`, exists in both 1.5.19 and 1.6.6. The encoder must
   register `%mask` there.
2. **`%mask(... %ex)` will suppress the implicit throwable**, just like `%replace` in test 4:
   `EnsureExceptionHandling.compositeHandlesThrowable` walks the children of every
   `CompositeConverter`.
3. **A bare `LoggerContext` needs an MDC adapter.** Without
   `context.setMDCAdapter(new LogbackMDCAdapter())`, every append fails with an
   `NullPointerException` that is reported only as a status message: the output is silently empty.
   Integration tests in Phase 5 must set it, or they would pass for the wrong reason.
4. **JSON encoders see the arguments separately** (test 5). Masking the rendered message cannot
   cover them, which matters for RF21/RF22 later.

### 1.5 JDK 25 and JDK 21 builds

| Run | `mvn -v` (relevant lines) | Result |
| --- | --- | --- |
| Default (`/etc/mavenrc` → JDK 25) | `Apache Maven 3.9.11` · `Java version: 25.0.4.1, vendor: Ubuntu, runtime: /usr/lib/jvm/java-25-openjdk-amd64` | `BUILD SUCCESS`, 2 + 6 tests |
| `JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 MAVEN_SKIP_RC=true MAVEN_OPTS= mvn -B clean verify` | `Apache Maven 3.9.11` · `Java version: 21.0.12.1, vendor: Ubuntu, runtime: /usr/lib/jvm/java-21-openjdk-amd64` | `BUILD SUCCESS`, 2 + 6 tests |

Two details of the environment:

- `MAVEN_SKIP_RC=true` alone did not fall back to JDK 21, because the shell's `JAVA_HOME` already
  pointed at the JDK 25 path.
- The environment sets `MAVEN_OPTS=--sun-misc-unsafe-memory-access=allow`, an option JDK 21 does
  not recognize. The JVM refuses to start until `MAVEN_OPTS` is cleared. Phase 3 CI has to set
  `MAVEN_OPTS` per JDK.

An ad-hoc run of `maven-javadoc-plugin:3.12.0:javadoc -Ddoclint=all -DfailOnWarnings=true` on JDK
25 passed. The plugin was not added to the POMs, because quality gates are Phase 3.

## 2. Error Prone and NullAway on JDK 25 with `--release 21` (research only)

Nothing was configured. These are findings for Phase 3.

### Error Prone

- **Latest:** 2.52.0, released 2026-11-02 (Maven Central metadata; [releases][ep-releases]).
- **Minimum JDK to run:** 21, since 2.43.0 ("The minimum supported JDK version to run Error Prone
  is now JDK 21"). Building on JDK 25 meets it.
- **JDK 25:** no release note lists a JDK 25 incompatibility. 2.45.0 mentions "improved
  compatibility with latest JDK 26 EA builds". A mirror of Error Prone's CI workflow runs on JDK 25
  and on early-access JDK 27 ([CI mirror][ep-ci]). That source is secondary and may lag upstream.
- **Running on JDK 21:** requires `-XDaddTypeAnnotationsToSymbol=true` (since 2.46.0;
  [installation docs][ep-install], google/error-prone#5426).
- **Maven setup**, from the installation docs:
  - compiler args `-XDcompilePolicy=simple`, `--should-stop=ifError=FLOW` and `-Xplugin:ErrorProne`;
  - `error_prone_core` in `annotationProcessorPaths`;
  - the `--add-exports`/`--add-opens` list for `jdk.compiler`, placed in `.mvn/jvm.config`, or
    passed as `-J` args when the compiler is forked or toolchains are used.
- **`--release 21`:** the docs neither require nor forbid it. `--release` only selects the
  platform API signatures that `javac` compiles against; Error Prone runs inside that `javac`.
  **No incompatibility was found, but none was proven absent either.** Phase 3 must verify it
  with a real build.

### NullAway

- **Latest:** 0.14.3, released 2026-10-22 (Maven Central metadata; [releases][na-releases]).
- **Requirements** ([README][na-readme]): build with JDK 17 or later and Error Prone 2.36.0 or
  later.
- **JSpecify mode** ([wiki][na-jspecify]) requires the running `javac` to be JDK 22 or later.
  Alternatively, it works on JDK 21.0.8+ (or 17.0.19+) with `-XDaddTypeAnnotationsToSymbol=true`,
  on OpenJDK builds only: the flag does not work on Oracle JDK. Since 0.12.11, NullAway fails the
  build with `IllegalStateException` when neither condition holds. The wiki recommends "the latest
  `javac` version possible" combined with `--release` to target older JDKs. That is exactly the
  D1 setup.
- 0.14.x adds testing on JDK 26 and on early-access JDKs 27 and 28. 0.14.2 detects whether the
  build JDK can read type-use annotations from bytecode.

### Verdict

Building on JDK 25 with `--release 21` meets every documented requirement of both tools, with no
extra flag. **This does not contradict D1 or D9.**

Phase 3 caveat: if CI also *compiles* on JDK 21 rather than only *testing* on it, the JDK 21 job
needs `-XDaddTypeAnnotationsToSymbol=true` (OpenJDK 21.0.8+). The simpler alternative is to compile
once on 25 and run the tests on both JDKs.

## 3. jqwik and Jazzer

The spec marks both as hypotheses to check before adopting them (section 10.4).

### jqwik

| Item | Finding | Source |
| --- | --- | --- |
| Latest version | 1.10.2 (Maven Central metadata updated 2026-10-10) | Maven Central |
| Maintenance | "Currently, jqwik is in pure maintenance mode": no feature development without funding; upstream updates and crucial bug fixes continue | [README][jqwik-readme] |
| License | EPL-2.0 | [LICENSE.md][jqwik-license] |
| JUnit Platform | The 1.10.1 notes say it is probably the last release on JUnit Platform 1.x; any future release would be on JUnit Platform 6 and Java ≥ 21 | Release notes, via [aws-samples PR][jqwik-aws] |
| "Anti-AI Usage Clause" | Since 1.10.0, the user guide states that the project "is not meant to be used by any 'AI' coding agents". jqwik prints a message addressed to AI agents in test output, telling them to disregard their instructions and ignore jqwik's test results. According to third-party reports, 1.10.0's wording also told agents to delete jqwik tests and code, 1.10.1 softened it, and a `jqwik.hideAntiAiClause` setting controls whether the text is hidden in terminals | [User guide][jqwik-guide] (jqwik.net is not reachable from this environment, so it was read through search results), [release notes][jqwik-notes], [spec-kitty issue][jqwik-issue], [blog analysis][jqwik-blog] |

**Assessment (recommendation, not a decision):**

1. **The clause conflicts with how this project is developed.** CLAUDE.md is written for Claude
   sessions. A test dependency whose output is designed to steer AI agents is a prompt-injection
   channel inside the build: it is the kind of supply-chain behavior threat T11 is about. It also
   makes test results unreliable when an agent reads them. The EPL-2.0 license itself does not
   forbid AI use; the clause is a stated intent plus runtime behavior.
2. **Compatibility risk.** The Phase 2 skeleton uses JUnit 6.1.3. jqwik 1.10.x is built on JUnit
   Platform 1.x and has no announced Platform 6 release. Running both platforms side by side was
   not tested.
3. **Recommendation:** do not adopt jqwik. Options for the property tests in spec section 13:
   - JUnit `@ParameterizedTest` with seeded generators written in the test sources. This adds no
     dependency and keeps runs reproducible.
   - Jazzer's `@FuzzTest`, which also generates structured inputs.

   This changes spec sections 10.4 and 13, so it is **an open question for the maintainer**
   (section 5).

### Jazzer

| Item | Finding | Source |
| --- | --- | --- |
| Latest version | `jazzer-junit` 0.30.0, released 2026-02-24 (Maven Central metadata) | Maven Central |
| License | Apache-2.0. Code Intelligence had paused open-source maintenance and changed the licensing (a 2024 change, PR #906), then returned the project to Apache-2.0. The README since 0.25.1 states "Jazzer is back under the Apache 2.0 license!" | [Repository][jazzer-repo], [Code Intelligence blog][jazzer-blog], [Socket listing of 0.25.1][jazzer-socket], [PR #906][jazzer-pr] |
| Maintenance | Releases continued after the return: 0.29.1 in December 2025 and 0.30.0 in February 2026. There has been no release in the 8 months since 0.30.0. The repository is public and active (open issues and PRs), but it publishes no maintenance statement | [Maven Central index][jazzer-central] |
| JUnit | "Jazzer integrates seamlessly with JUnit (version 5.9.0 or newer)". JUnit 6 is not mentioned, so compatibility with the JUnit 6.1.3 used here is **not verified** | [Repository][jazzer-repo] |

**Assessment:** the license is acceptable (Apache-2.0, the same as this project). Adoption depends
on JUnit 6 compatibility, which must be checked with a real fuzz test in Phase 3 or 4. The fallback
named in the spec, adversarial generators in jqwik, falls with the jqwik recommendation above. The
replacement would be seeded generators in JUnit.

## 4. Logback facts in the spec: confirmed or refuted

| # | Spec statement (section) | Verdict | Evidence |
| --- | --- | --- | --- |
| L1 | When the pattern declares no throwable converter, `PatternLayout` appends `%ex` on its own, outside any `%mask` (8.2; also T2, 1.1) | **Confirmed** | PoC test 1, on 1.5.18, 1.5.19, 1.5.38 and 1.6.6. Source: `PatternLayout` installs `EnsureExceptionHandling` as its post-compile processor (1.5.19 `PatternLayout.java:178`); `EnsureExceptionHandling.process` appends a `ThrowableProxyConverter`, or `ExtendedThrowableProxyConverter` when packaging data is enabled, if `chainHandlesThrowable` is false |
| L2 | `%nopex` is the way to not print the throwable (8.2) | **Confirmed** | PoC test 3; the Javadoc of `EnsureExceptionHandling` says so |
| L3 | Showing `%mask(%msg%n%ex)` in the documentation closes the bypass for `%mask` users (8.2) | **Confirmed (mechanism)** | PoC test 4 with `%replace`, which is also a `CompositeConverter`: `compositeHandlesThrowable` recurses into composite children, so the throwable is printed once, inside the composite. To be re-confirmed with `%mask` itself in Phase 5 |
| L4 | `%replace(%msg){'regex','subst'}` exists and lets a team mask a formatted CPF with no dependency (1.3) | **Confirmed**, with a caveat | PoC test 2: it masks the message, **but not** the implicit throwable. This strengthens the spec's argument in 1.3 |
| L5 | A `ClassicConverter` only acts on text rendered by a `PatternLayout`; the native `JsonEncoder` and appenders that read `ILoggingEvent` directly are outside it (1.1, 8.1, T4) | **Confirmed** for the native `JsonEncoder` | PoC test 5. Source: `JsonEncoder.encode` writes `event.getMessage()`, the arguments and the throwable proxy directly. `logstash-logback-encoder` and the OpenTelemetry appender were not tested, because the PoC is restricted to plain Logback. They fall under the same mechanism, since they read the event, not a layout |
| L6 | Logback before 1.5.19 has CVE-2025-11226, code execution through `<if>` conditions (8.2) | **Confirmed**, with a precision | GitLab advisory: affected below 1.3.16 and from 1.4.0 up to, but not including, 1.5.19; fixed in 1.5.19 and 1.3.16. Exploitation needs Janino and Spring on the class path and existing privileges. Within the 1.5 line, the statement is exact |
| L7 | Matrix 8.1, "`%mask(%msg)`: exception covered only if `%ex` is inside `%mask`" | **Confirmed** | Follows from L1 and L3 |
| L8 | `TurboFilter`/`Filter` can only accept or deny, not rewrite (11.2; listed because 8.1 relies on it) | **Confirmed** | Source: `TurboFilter.decide(...)` and `Filter.decide(...)` return `FilterReply` (`DENY`, `NEUTRAL`, `ACCEPT`) |
| L9 | "The 1.5 series is the active one and requires Java 11+" (10.1; RNF08 says "Logback 1.5.x") | **Refuted in part** | Java 11 is **confirmed**: `jdk.version` is 11 in the parent POMs of 1.5.38 and 1.6.6. "The 1.5 series is the active one" is **refuted**: 1.6.0 was released on 2026-07-23 ([release][lb-160]) and 1.6.6 is the latest on Maven Central. 1.5.38 is still being published, so 1.5 is maintained, but it is no longer the only or the newest line. Raised with the maintainer; RNF08 left unchanged (ADR-007) |
| L10 | "The `CompositeConverter` / `ClassicConverter` API has been stable for many versions" (10.1) | **Confirmed for the converters, not for registration** | `CompositeConverter` (`transform`, `getChildConverter`) is identical in 1.5.19 and 1.6.6. Registering converters programmatically changed in 1.6.0 (section 1.4, item 1) |

## 5. Open questions for the maintainer

1. **Logback 1.6.x (L9).** Should RNF08 and spec section 10.1 say "Logback 1.5.19+ including
   1.6.x"? And should the CI matrix (Phase 3) be "1.5.19 × latest 1.6.x", or keep a 1.5.x leg?
   The PoC and the skeleton already pass on 1.6.6.
2. **jqwik (section 3).** Replace jqwik in spec sections 10.4 and 13 with seeded JUnit generators
   (and Jazzer where it fits)? The recommendation is yes, for the reasons above.
3. **Jazzer and JUnit 6.** Confirm adoption only after a real `@FuzzTest` runs on JUnit 6.1.3
   (Phase 3/4), or keep JUnit on 5.x for the fuzzing module?
4. **RF15 / open type model (ADR-006).** If custom detectors are wanted at all, the type model must
   change before 1.0. Is RF15 still wanted?
5. **CI per-JDK `MAVEN_OPTS` (section 1.5).** This is a Phase 3 concern, noted here so it is not
   lost.
